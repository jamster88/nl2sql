# Changelog

Every version from the first, newest first, with the major artifacts each one
created, updated or fixed, and the image tags it published.
[`CHANGELOG_SIMPLE.md`](CHANGELOG_SIMPLE.md) is the same history as one line
per change.

**Versions.** The number is the agent's: `__version__` 5.1.2 is published as
the tag `v5_1_2`, and a tag with fewer components names a line
(`v5_1` is 5.1.x). The app images -- `nl2sql-agent`, `nl2sql-gui`,
`nl2sql-review`, `nl2sql-review-gui`, `nl2sql-console-gui`, the five
`nl2sql-desktop-build` platforms, since v5_5 `nl2sql-mlflow` and
`nl2sql-mlflowdb`, since v5_6 `nl2sql-curate-gui`, since v6_0
`nl2sql-ldap`, `nl2sql-auth`, `nl2sql-directory-gui` and
`nl2sql-mlflow-proxy`, and since v6_3 `nl2sql-proxy` in place of the six
pages' -- are released
together at one number, which
[`tests/docs/test_versions.py`](../tests/docs/test_versions.py) holds every
declaration in the repository to. The dataset images --
`nl2sql-retail-postgres`, `nl2sql-rag-vectordb`, `nl2sql-rag-chunkdb` --
version independently, because their content changes independently of the
code; each is listed under the release it shipped with. A version marked
*unpublished* is a checkpoint in the repository that published no tag.

**Tags never move.** A published tag is never re-pushed: a correction to
something already published is a new patch version and a new tag. Every
versioned tag below is still on Docker Hub as it was first published, with one
exception from before the rule existed (the `v4_5` desktop tags, see v4_5_1);
only the `latest` tags move, which is what they are for. Publish dates are
Docker Hub's, in UTC; release dates are the repository's.

**Artifacts.** Paths are relative to the repository root. Tests are named by
file where a file is new; the tests a version merely extended are summarised.

- **arch7.3's Phase 6: the grain check** (2026-10-10). The Static Validator refuses a query that joins two tables of different grains without bringing them to one. It is the one part of arch7 inside the pipeline rather than around it, so it holds for every run of every configuration, the ensemble on or off. `agent/nl2sql_agent/grain.py` (new). **The grains, measured**: `read_grains` takes every table of the catalog with a foreign key to the date dimension's key -- its first such column in column order, the date it is stamped with -- and gives it the coarsest period of `GRAIN_PERIODS` that holds at most one of the table's distinct dates in each; a table with two dates in some fiscal week is daily. `Database.dates_per_period` (new) is the read: one READ ONLY statement a table on the reader's pool, under the statement timeout, a count a period. On this catalog eight tables are stamped with a date -- three daily, three weekly, two monthly -- and each is read in under 100 ms. They are read once a process, beside the label map, into `ContractResources.grains` (`Nl2SqlAgent.grains()`). **The rule**: `mismatches`, over `completeness.read_query`'s reading and the statement itself, between two tables that are both added up and whose grains differ. *On the date*: the two joined date to date -- directly, or each through the date dimension, or in the WHERE -- and the finer not first rolled up to the coarser's period. *On no date*: the two joined on other columns alone, with no date and no period among them, and the coarser still bringing a row for every period -- read row by row, or rolled up keeping its date or its period. `message` words each from the grains, with no table named in code: "fact_item_cogs is monthly -- one date in each fiscal month -- and fact_pos_retail_sales is daily; joined on the date, each fiscal month's row of fact_item_cogs meets only the rows of fact_pos_retail_sales for that one date. Roll fact_pos_retail_sales up to the fiscal month (fiscal_year, fiscal_month_num) and join on those columns, not on the date.", and "... are joined on no date or period, so each row of fact_pos_retail_sales meets every fiscal month's row of fact_item_cogs. Join them on the fiscal month as well (fiscal_year, fiscal_month_num), or roll fact_item_cogs up past the fiscal month before joining it." **Where it runs**: `validate.validate(sql, *, allowed_tables=None, grains=None)` adds each mismatch as a static issue after the statement's own, and `graph.py`'s `_validate_static` passes the grains, so a refusal goes to the Repair Agent and spends the shared attempts budget as any static issue does. `repair.py` knows the issue by its words (`GRAIN_ISSUE`) and hands it to the generator as written, with one line more -- the tables, the filters and the measure are right, and only the join is to change -- and no model call. The SQL console calls the validator without grains, as section 3.9 leaves it, so its verdict on a pasted query does not include this check -- `console/README.md` says so, and it is a question for the next specification, since the verdict is otherwise the agent's gates with the agent's code. **What passes**: the finer rolled up to the period and joined on it, as CTEs or as subqueries; a join on the period through two calendars; the coarser rolled up past its period and joined on product alone; the coarser held to one period by a filter; and everything the rule cannot read -- a join it cannot follow, a table read twice, a roll-up behind `DISTINCT ON` or a window. **Settings**: `GRAIN_CHECK_ENABLED` (on) and `GRAIN_PERIODS` (`fiscal_year+fiscal_week_num,fiscal_year+fiscal_month_num`: the periods finest first, each the date dimension's columns that name one), both forwarded by compose; a `GRAIN_PERIODS` that does not parse stops the agent at start. **Standing down**: when the grains cannot be read -- no date dimension, a period column it does not have, a database error -- the reason is kept in `ContractResources.errors["grains"]`, the validator runs without the check for the life of the process, and the log says so once. **The benchmark**: every configuration's report ends with a GRAIN CHECK block -- the reference queries the check would refuse with the grains that run read, which must be none and makes the exit code non-zero otherwise, and the runs it sent to repair with how each ended, right, wrong or without rows -- in `--json` (`grain`, and each result's `grain_repairs`) and as MLflow metrics (`grain.references_refused`, `grain.repaired_runs`, `_right`, `_wrong`, `_failed`). Tests: `tests/agent/test_grain.py` (new, 82) -- the grains read from a fake database's dates, each failing shape with its message word for word, each right shape passing; `tests/grain_fixture.py` (new), the catalog's grains as a fixture, held to the live catalog under `--run-docker`; `tests/benchmarks/test_questions.py` holds all fifteen references to the check, offline against the fixture and live against the catalog; and `tests/agent/test_graph.py` runs the trap through the pipeline -- refused, repaired, answered. `arch_v7.svg` draws it in a note of its own, and `agent/README.md` describes it under the pipeline.

## v5_6 (5.6.0) -- 2026-10-03

SQL snippets: pieces of SQL that have been run against this database, each
beside what it means in a question's words. A snippet is a join (how two
tables meet, and what the join is for), a filter ("store brands" is
`p.is_private_label`), a measure (how net sales or the average basket is
calculated) or a dimension (a fiscal quarter labelled the way people say
it). They are curated in a tracked document,
`context_questions/sql_snippets.md`, which ships 32 of them, and loaded into
a store of their own. That store is a fifth retriever for the agent,
separate from the knowledge base, the golden pairs and the fix stores. Each
question's snippets are found by keyword phrase and by meaning, and the SQL
Generator sees those whose tables are all in scope. A fourth web interface,
the curation interface, writes snippets, golden pairs, corrections and
completions directly, without a submission. Each one is run against the
retail database before it can be saved. Promotion from the review queue
runs the golden SQL first as well. Thirteen tags were published, the
curation interface's for the first time.

### Created
- `context_questions/sql_snippets.md` -- the snippet document: 32 snippets (8 joins, 10 filters, 10 measures, 4 dimensions), each with its kind, tables, keyword phrases, meaning, the FROM clause it applies to, its SQL and a note. Every one was run against the retail database, and the counts in the notes are what it returned.
- `rag/ragproc/snippets.py` -- the document's strict parser (a snippet that does not parse is an error, not skipped); the store's three tables (`sql_snippets`, `sql_snippet_vectors`, `sql_snippet_source`); the keyword matcher `sql_snippets_keyword_match()`, in SQL, which matches each keyword and the name as a phrase whose words must all be in the question, weighted by IDF; the read-only role; and the document hash a complete load records.
- `rag/07_load_snippets.py` -- loads the document into the store, removes snippets no longer in it, (re)creates the agent's `snippets_reader` role with SELECT and nothing else, and embeds only the meanings that changed, so a load with nothing new needs no embedding host. A failed embed exits non-zero and records no hash, so the next start loads again.
- `agent/nl2sql_agent/snippets.py` -- `SnippetLibrary`: candidates from the keyword matcher and the 20 nearest meanings; a snippet qualifies on a matched phrase or on meaning alone at cosine 0.62.
